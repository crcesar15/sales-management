## Executive Summary

Fix API authorization, mass-assignment, resource serialization, and collection pagination. Create API Form Requests for vendors and purchase orders, add `authorize()` to the five API controllers that lack it, return `PurchaseOrderResource` from the purchase-orders API, fix `CashRegisterShiftResource` and `StockTransferResource` serialization, and add pagination meta to `ApiCollection`. `PurchaseOrderResource` and `PurchaseOrderCollection` already exist in the codebase and are used as-is. This plan depends on Plan 01-03 because it assumes the settings API controller cache invalidation is already correct.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Public API controllers (`routes/api.php`) | Anonymous/token-authenticated requests cross here; authorization and input validation are enforced. |
| API controllers → Service layer | User input reaches business logic; controllers must pass only validated data. |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-01-04-A1 | Tampering | API controllers (FIX-01) | mitigate | Replace `$request->all()` with `$request->validated()` from API Form Requests. |
| T-01-04-A2 | Elevation of privilege | API controllers (FIX-02) | mitigate | Add `$this->authorize(PermissionsEnum::X->value, auth()->user())` per action. |
| T-01-04-A3 | Information disclosure | `CashRegisterShiftResource` / `StockTransferResource` (FIX-03/04/05) | mitigate | Use `whenLoaded()` and explicit date/identifier fields; return Resources instead of raw models. |
</threat_model>
